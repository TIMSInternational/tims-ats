# Sprint 1.7 — 360° Evaluation Module (Shell) — Design Spec

**Base:** `main` @ `44c5d55` (post Sprint 1.6). **Branch:** `worktree-sprint-1.7-360-eval`.
**Status:** DESIGN — awaiting Federico's ruling on the 3 load-bearing decisions (§7) before the executable plan is finalized and built.

## 1. Goal & scope
Ship the **greenfield 360° evaluation CRUD + aggregation core** ("the shell"): a
`cycle → rater-set → per-rater response → aggregation → publish` pipeline with three actor
experiences (admin runs cycles; raters complete assignments; subjects read a published,
anonymized report) and a new least-privilege RBAC module.

**Explicitly OUT of scope (deferred):**
- **Sentiment analysis** on free-text comments → Phase 2 Sprint 2.3b's shared `climate-sentiment-analyzer`
  tool (build once, reuse for Climate + 360 — do NOT build a second sentiment pipeline). The shell stores
  comments as plain text; no NLP.
- A full relational **`Competency`** table (see §7 decision B) — the shell uses config/enum competency keys.
- **External/API-key raters** (customer/vendor 360) — defer; reuse the 1.6 external surface later if wanted.

## 3. Proposed data model (new `packages/db/prisma/schema/evaluation360.prisma`)
Enums (PascalCase name / snake_case values, per db.md):
- `ReviewCycleStatus { draft open closed published }`
- `RaterRelationship { self manager peer direct_report }`  *(external deferred — §1)*
- `RaterAssignmentStatus { pending submitted }`

Models (all org-scoped, `id` UUID, `createdAt`/`updatedAt`, `@@index([organizationId])`, explicit `onDelete`):
- **`ReviewCycle`**: `organizationId, name, status(draft), opensAt?, closesAt?, publishedAt?, createdById → User`.
- **`RaterAssignment`**: `organizationId, cycleId → ReviewCycle(Cascade), subjectUserId → User, raterUserId → User,
  relationship, status(pending), submittedAt?`. `@@unique([cycleId, subjectUserId, raterUserId])`,
  `@@index([raterUserId])`, `@@index([subjectUserId])`, `@@index([cycleId])`.
- **`RaterResponse`**: `organizationId, assignmentId → RaterAssignment(Cascade), competencyKey(String),
  rating(Int 1–5), comment(String? ≤5000)`. `@@unique([assignmentId, competencyKey])`, `@@index([assignmentId])`.
Migration = ONE additive file creating the enums + 3 tables + indexes + FKs + **an RLS block per table** (hire_predictions template).

## 4. RBAC design (new module `evaluation360`) — FINAL (post Slice-2 review)
- Add `'evaluation360'` to `MODULES`.
- `MATRIX` grants (least privilege):
  - `super_admin`, `hr_admin` → `create/read/update/delete` @ `organization`. **Admin procedures are additionally
    gated by `requireOrgScope(ctx.access)`** — a module+action grant alone does NOT enforce scope, so the org gate
    is what keeps sub-org roles out of the admin surface.
  - `employee` → `read/update` @ `own` (my rater tasks + submit; my published report). **Self-service endpoints are
    IDENTITY-anchored** (`raterUserId === ctx.user.id` for tasks/submit; `subjectUserId === ctx.user.id` for the
    report) via hard where-filters — NOT scope-aware `assertScoped`/`scopeWhereFor` (which would let an org-scoped
    admin bypass rater ownership). No `create` grant (submit is `update`).
  - `hrbp` / `leader` → **DEFERRED** (no evaluation360 grant in the shell). Scoped unit/team completion monitoring
    is a real future enhancement (needs subject→unit/team resolution); the admin reads are org-only for now.
  - `committee` → none.
- Targeted prod grant seed at ship (per-org, like Sprint 1.6): global `permissions` rows for the new
  module:action pairs + per-org grants for the roles above. Never full `seed.ts`.

## 5. Routers / services / repos (all `permissionProcedure('evaluation360', …)` + `assertScoped` for by-id)
- **Admin (`organization` scope):** `createCycle`, `openCycle`, `closeCycle`, `publishCycle` (status transitions,
  atomic guarded), `assignRaters` (bulk, transactional, dedup on the unique key), `listCycleProgress` (completion %).
- **Rater (`own`/assigned scope):** `myRaterTasks` (assignments where `raterUserId = ctx.user.id`, status pending),
  `submitRatings` (own assignment ONLY — `assertScoped('raterAssignment', …)`; transactional; flips status→submitted).
- **Subject (`own` scope):** `myReport` — aggregated, **anonymized** per-relationship averages, ONLY when cycle
  status = published; **min-N suppression** via `aggregate.ts` (§7 decision C). Never expose a single rater's raw row.
- Clean architecture: router (zod) → service (transitions, aggregation, anonymity) → repository (`tenantDb`, `select`).

## 6. UI surfaces (all i18n es/en, Skeleton/ErrorState/EmptyState per frontend.md)
- **Participant "My 360"** (`/my-360`, employee): pending rater tasks (rating form) + (when published) my report.
- **Admin 360** (`/talent/360`, hr_admin/super_admin): create cycle, assign raters, monitor completion %, publish.
- Nav wiring in `manifest.ts` + `routes.ts` in lockstep (NO-DRIFT test).

## 7. ✅ LOCKED DECISIONS (Federico-approved 2026-07-13)
- **A. Scope = FULL shell** (5 slices + a 6th adversarial anonymity review).
- **B. Competency model = config enum, FRESH small 360 set** in `packages/shared` (~6–8 keys:
  leadership, communication, collaboration, execution, adaptability, integrity). No relational `Competency`
  table. Unify with LIA/PCA later.
- **C. Anonymity = min-3 for peer + direct_report buckets; SELF shown; MANAGER shown attributed.** A deliberate,
  documented deviation from the platform min-5 (`aggregate.ts`), justified by 360 semantics. Implement a
  360-specific `suppressBelowMin3` (do NOT change the shared `suppressBelowMin5`/`MIN_AGGREGATE_SIZE=5`).

### (original decision framing, for the record)
**A. Shell scope / slice count.** Recommend the FULL shell = 5 slices (schema+RBAC → admin CRUD+assign →
rater tasks+submit → aggregation+publish+report → participant & admin UI), each SDD + Codex-gated, then a 6th
adversarial anonymity review. Alternative: backend-only now, UI later. *Recommendation: full shell.*

**B. Competency model.** Recommend **config-driven `competencyKey` (enum/constant list)** for the shell — a fixed
set of ~6–8 360 competencies defined in `packages/shared` (e.g. leadership, communication, collaboration,
execution, adaptability, integrity), NOT a relational `Competency` table (deferred). Simpler, matches "shell,"
avoids a premature table the whole platform lacks. Open sub-question: reuse the **LIA/PCA competency taxonomy**
for comparability, or a fresh 360 set? *Recommendation: fresh small 360 set now; unify later.*

**C. 🔑 Anonymity threshold (the critical one).** Platform k-anon standard = **min-5** (`aggregate.ts`). But 360
peer/report buckets are usually small (3–4 people); min-5 would suppress almost all peer feedback → feature
useless for small teams. 360 industry norm = **min-3 per relationship bucket**; SELF shown (it's you); MANAGER
shown attributed (manager feedback is conventionally non-anonymous, usually 1 person). *Recommendation: min-3 for
peer + direct_report buckets, self shown, manager shown attributed — a deliberate, documented deviation from the
platform min-5, justified by 360 semantics.* This is a privacy/utility policy call on real employee data →
**Federico must rule.** (Alt: keep strict min-5, accept heavy suppression; or make min-N configurable per cycle.)
