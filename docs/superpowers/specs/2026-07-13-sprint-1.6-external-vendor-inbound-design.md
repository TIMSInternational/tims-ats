# Sprint 1.6 — External Vendor Inbound-Write (Submit Validation Result) — Design Spec

**Date:** 2026-07-13
**Sprint:** Phase 1, Sprint 1.6 (per `tims-ats-master-build-plan`)
**Base branch:** `main` @ `7c0350a`
**Depends on:** the external API-key auth surface already live on `main` (PR #74 — `externalProcedure`, `ApiKey`, scopes, per-key rate limit, audit).

## 1. Purpose

Let an **external vendor** (a background-check / medical / assessment provider, authenticated by an org-scoped API key) **submit the result** of a preemployment validation that TIMS staff previously initiated. Today the external API surface is structurally **read-only** (`routers/external.ts` = two `assessment:read` queries); the signed contract wants vendors to be able to send verification results *back in*. This closes that gap with a single additive, API-key-scoped inbound **write**.

## 2. Grounding findings (verified against live code)

These corrected the original plan framing:

1. **The API-key auth infra already exists on `main`** (PR #74) and is reused as-is: `externalProcedure` / `externalPermissionProcedure(module, action, requiredScope)` (`packages/api/src/trpc.ts:222-247`), `requireApiKey` middleware + per-key rate limit (`trpc.ts:197-220`), `resolveApiKeyPrincipal` fail-closed (`access/external-auth.ts:31-42`), `buildExternalAccessUser` → `roles: ['external']`, the `ApiKey` model (`integration.prisma:81-101`, org-scoped, SHA-256 hashed, `scopes Json`, suspended-org lockout in `external-auth.repository.ts:31-35`).
2. **The external surface is a mutation-free read surface today** — `externalProcedure` has only ever defined `.query()`. This sprint adds the **first external mutation**.
3. **Write target = `PreemploymentValidation`** (`offer.prisma:60-81`): `result Json?`, `status String @default("pending")`, `type String`, `isBlocking Boolean`, keyed by `offerId`; **`completedById → User`** is the only "who completed it" FK — a vendor API-key principal has **no `User` row**, so writing `completedById` would violate that FK. → schema change (§4).
4. **No "External Vendor" role** — the principal is the generic `external` role whose *only* grant is `assessment:read` (`seed-access-matrix.ts:119-121`). A validation write needs a new grant + a new module in the canonical `MODULES` list (`packages/shared/src/types/permissions.ts:3-10`, policed by `tests/access/permission-vocabulary.test.ts`).
5. **`type`/`status` are plain `String` + zod-enum validation**, not DB enums (staff `updateValidation` uses `status: z.enum(['pending','passed','failed','waived'])` at `routers/offer/validations.ts:33`). This sprint **follows that existing pattern** (zod-enum validation, no DB enum) — deliberately unlike Sprint 1.1.f, because we're writing into an existing String column with an established validation pattern.
6. The `feat/access-external-api` branch is **stale/superseded** (content-identical to main, ~53k lines behind). Branch from `main`; use that branch only as a reference for how the read surface was built.

## 3. Decisions (confirmed with Federico)

- **Transport = tRPC-over-bearer.** Add an external mutation on the existing surface (vendor POSTs a JSON body to `/api/trpc` with `Authorization: Bearer <key>`). Reuses all hardened auth/scoping/rate-limit/audit. A plain-REST adapter is a documented fast-follow if a specific vendor needs it — not in v1.
- **Provenance = add `completedByApiKeyId` FK.** Additive nullable FK on `PreemploymentValidation` → `ApiKey` (`onDelete: SetNull`), recording which vendor key submitted the result. First-class, queryable provenance; `completedById` (staff) stays null on vendor writes.
- **New least-privilege `validation` module** (not reusing broad `offer`): the `external` role gets exactly `validation:update`, so it can never reach any `offer` endpoint even in principle (no latent footgun).
- **v1 = write-only.** Submit a result to an existing pending validation by id (vendor obtains the id out-of-band). No vendor-facing discovery/list endpoint and no per-key validation-*type* restriction — both are documented future hardening.

## 6. Endpoint / service / repository (mirror the read surface)

- `packages/api/src/dto/external-validation.ts` — **versioned v1**:
  - Request: `{ apiVersion: z.literal('v1'), validationId: z.string().uuid(), status: z.enum(['passed','failed']), result: z.record(z.unknown()) (≤100 000 stringified chars), notes: z.string().max(5000).optional(), externalReference: z.string().max(200).optional() }`.
  - Response mapper → a stable v1 DTO (`{ id, status, completedAt }`), never leaking internal columns.
- `packages/api/src/repositories/external-validation.repository.ts`:
  - `getValidationForSubmit(orgId, validationId)` — explicit `select` (`{ id, status }`), org-scoped.
  - `submitValidationResult(orgId, validationId, apiKeyId, { status, result, notes })` — **atomic guarded write**: `updateMany({ where: { id: validationId, organizationId: orgId, status: 'pending' }, data: { status, result, notes, completedByApiKeyId: apiKeyId, completedAt: new Date() } })`; returns the affected count. Count 0 ⇒ caller throws.
- `packages/api/src/services/external-validation.service.ts`:
  - `submitResult(externalAuth, input)` — verify the validation exists in `externalAuth.organizationId` (else NOT_FOUND, no info leak); perform the atomic write; if count 0 (not pending / gone) ⇒ CONFLICT ("validation is not open for submission"); write a **fail-closed audit** record (`apiKeyId`, action `validation.submit`, resource = validationId, PII-free), mirroring `external-assessment.service`; return the v1 response DTO.
- `packages/api/src/routers/external.ts` — add:
```ts
submitValidationResult: externalPermissionProcedure('validation', 'update', 'validation:write')
  .input(ExternalValidationSubmitV1)
  .mutation(({ ctx, input }) => externalValidationService.submitResult(ctx.externalAuth!, input)),
```

## 7. Security invariants (must hold)

- **Org isolation:** every read/write is filtered by `externalAuth.organizationId`; a key for org A can never touch org B's validations (defense-in-depth over RLS).
- **Scope narrowing:** the endpoint requires the `validation:write` scope in `ApiKey.scopes[]` AND the `external` role's `validation:update` grant — both must pass.
- **Pending-only, atomic:** results can only be submitted to a `pending` validation, via a single atomic `updateMany` guard — no overwrite of a finalized result, no double-submit race (TOCTOU-safe, matching the #105 audit pattern).
- **Bounded inputs:** all strings/JSON bounded (§6); no `z.any`/`.passthrough`; status restricted to `passed`/`failed` (a vendor cannot `waive` or reset to `pending`).
- **No staff-FK violation:** vendor writes set `completedByApiKeyId`, never `completedById`.
- **Audit:** every submission writes a PII-free audit record keyed on the apiKeyId.
- **Rate-limit:** endpoint named `submitValidationResult` (no `medical` substring → avoids the AI-tier miscategorization at `rate-limit.ts:142`); gets the mutation tier + the per-key limit.

## 8. Testing

- **Service** (mock repo + audit): submit to pending → atomic write called with `completedByApiKeyId` + audit written + v1 DTO returned; submit where updateMany count 0 → CONFLICT; validation in another org → NOT_FOUND; audit failure fails closed.
- **Repository** (mock db): the `updateMany` guard shape (`where: { id, organizationId, status: 'pending' }`) and explicit selects.
- **DTO** (pure): v1 request validation (bad status / over-bound result / missing apiVersion rejected) + response mapper shape.
- **Access** (mirror `external-api-key-auth.test.ts`): a key whose `scopes[]` omits `validation:write` is denied; a key with it is allowed; the `external` role resolves a `validation:update` grant.
- **Vocabulary** (`permission-vocabulary.test.ts`) stays green with `validation` added to MODULES + matrix.
- **Schema** (dmmf): `PreemploymentValidation.completedByApiKeyId` present + nullable + relation.
- All mock/dmmf-based (CI has no live DB).

## 9. Scope boundary (explicitly NOT in v1)

- No plain-REST/webhook route (tRPC-over-bearer only; REST adapter is a future fast-follow).
- No vendor-facing discovery/list endpoint (vendor gets the validationId out-of-band).
- No per-key validation-*type* restriction (a key can submit any pending validation in its org).
- No staff UI surfacing `completedByApiKey` provenance (future; the column is populated + queryable now).
- No change to the staff `updateValidation` path or the `LegalCheck`/`OfferApproval` models.
- No new user-facing strings → no i18n.
