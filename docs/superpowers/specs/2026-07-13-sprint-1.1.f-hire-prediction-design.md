# Sprint 1.1.f — HirePrediction Snapshot at Hire Time (Design Spec)

**Date:** 2026-07-13
**Sprint:** Phase 1, Sprint 1.1.f (per `tims-ats-master-build-plan`)
**Depends on:** Sprint 1.5 FIT Engine (shipped, PR #124, main `03a489a`)
**Closes:** Phase 2 Sprint 2.3d tool-26 (Quality-of-Hire Analyst) instrumentation gap
**Base branch:** `main` @ `03a489a`

## 1. Purpose

At the moment a candidate is converted to an employee, capture an **immutable snapshot** of the FIT
prediction the system made about them. `FitScore` rows are mutable (upserted per `(candidateId, vacancyId)`)
and can change or be recomputed after a person is hired, so the prediction that actually informed the hire
decision is otherwise lost. This sprint records that prediction at hire time so a future **Quality-of-Hire
Analyst** (Phase 2, tool-26) can later correlate *predicted* fit against *actual* post-hire performance.

This sprint is **instrumentation only** — it produces the data. No analyst UI or query is built here (YAGNI;
that is Phase 2 tool-26). The write is wired onto a real, always-called path (`convertToEmployee`), so it is
live data accumulating from day one, not dead code.

## 2. Grounding findings (verified against live code, not assumptions)

These corrected the original plan framing and drive the design:

1. **There is no `Employee` model.** "Converting to employee" creates a **`User`** row
   (`packages/db/prisma/schema/user.prisma`). There is no `employeeId`; the new `User` has no FK back to the
   candidate/offer (only a matching email). Quality-of-hire joins therefore go through `User`.
2. **The hire trigger is `offer/lifecycle.ts` `convertToEmployee`** — a `permissionProcedure('offer','create')`
   keyed on **`offerId`**, wrapped in a `db.$transaction` that: creates the `User`, creates an
   `OnboardingPlan` (+ tasks), optionally a `UserTeam`, and flips `Offer.status → 'converted'`. It does **not**
   touch `Application.status`. The logic is **inline in the router** using `tenantDb as db` directly (an
   existing violation of "routers never import db" — we do not refactor it this sprint, per decision below).
3. **IDs in scope at hire time:** `organizationId`, `candidateId`, `vacancyId`, `offerId` (all before the tx),
   plus the new `userId` (only *after* `tx.user.create`, inside the tx). `offer.applicationId` exists but is
   **nullable**.
4. **`FitScore`** (`assessment.prisma`, `@@unique([candidateId, vacancyId])`) is **mutable** and may be
   **absent (null)** or **partial** (`isPartial` — true for most candidates today because no assessment writer
   exists yet). The existing reader `fitEngineRepository.getFitScoreForExplain` omits `weights`, `isPartial`,
   and `calculatedAt` — a fuller reader is needed for a complete snapshot.
5. **Snapshot house-style precedent:** the `Offer` model freezes comp values (salary/benefits Json) at offer
   time rather than referencing live rows; `StageMovement` is an append-only event log. House style for the
   new table: `organization_id` + FK columns + frozen `Json` blobs + a captured-at timestamp + its own RLS
   `tenant_isolation` policy **in the same migration**.

## 3. Decisions (confirmed with Federico)

- **Always snapshot (1:1).** Every hire creates exactly one `HirePrediction`. If the candidate has no FIT
  score at hire time, the row is still created with a null score and `predictionStatus: 'none'` — "hired
  without a prediction" is itself a Quality-of-Hire signal.
- **Add cleanly, do not refactor the hire flow.** Introduce a new `hire-prediction` repository + service that
  follow clean architecture; call them from *inside* the existing `convertToEmployee` transaction. Do **not**
  rewrite the (currently inline) `convertToEmployee` logic — minimize risk to a working, business-critical
  hire path.
- **Atomic — write the snapshot inside the existing transaction.** Guarantees the 1:1 invariant and a
  consistent read. Risk (a snapshot bug could block a real hire) is mitigated by keeping the snapshot logic a
  well-tested pure builder plus two trivial queries. Accepted tradeoff over best-effort-after-commit (which
  could silently miss a snapshot and break 1:1).

## 4. Data model

New file `packages/db/prisma/schema/hire-prediction.prisma`:

```prisma
model HirePrediction {
  id             String   @id @default(uuid()) @db.Uuid
  organizationId String   @map("organization_id") @db.Uuid

  userId        String  @map("user_id") @db.Uuid          // the new hire (User row)
  candidateId   String  @map("candidate_id") @db.Uuid
  vacancyId     String  @map("vacancy_id") @db.Uuid
  offerId       String  @unique @map("offer_id") @db.Uuid // 1 prediction per conversion (idempotency guard)
  applicationId String? @map("application_id") @db.Uuid   // nullable — Offer.applicationId is optional

  // Frozen FIT prediction snapshot (all nullable — candidate may have had no/partial score)
  overallScore     Float?    @map("overall_score")
  breakdown        Json?                                   // frozen FitBreakdown at hire time
  weights          Json?                                   // frozen weight profile used
  isPartial        Boolean?  @map("is_partial")
  fitCalculatedAt  DateTime? @map("fit_calculated_at")     // when the snapshotted score was originally computed
  predictionStatus String    @map("prediction_status")     // 'scored' | 'partial' | 'none'

  hiredById  String   @map("hired_by_id") @db.Uuid         // ctx.user.id who performed the conversion
  capturedAt DateTime @default(now()) @map("captured_at")
  createdAt  DateTime @default(now()) @map("created_at")
  updatedAt  DateTime @updatedAt      @map("updated_at")

  @@index([organizationId])
  @@index([userId])
  @@index([vacancyId])
  @@map("hire_predictions")
}
```

**Deliberate: scalar FK columns + explicit DB foreign-key constraints in the migration** (mirroring the 1.5
`role_family_weight_profiles` `organization_id` FK), **not** Prisma relation fields on User/Candidate/Vacancy/
Offer. Rationale: nothing needs relation navigation from those core models yet; declaring Prisma relations
would force back-relation edits to 5 core schema files for no current consumer (YAGNI). The Phase-2 analyst can
add relations when it needs them. Referential integrity is still enforced at the DB level via the FK
constraints.

`predictionStatus` mapping: `'scored'` = a non-partial FitScore existed; `'partial'` = a FitScore existed with
`isPartial = true`; `'none'` = no FitScore row for `(candidateId, vacancyId)` at hire time.

## 5. Migration (additive, single file, includes RLS)

New migration `packages/db/prisma/migrations/<ts>_add_hire_predictions/migration.sql`:
1. `CREATE TABLE "hire_predictions" (...)` with the columns above.
2. FK constraints: `organization_id → organizations(id) ON DELETE CASCADE`; `user_id → users(id)`;
   `candidate_id → candidates(id)`; `vacancy_id → vacancies(id)`; `offer_id → offers(id)`;
   `application_id → applications(id)` (nullable). (Exact `ON DELETE` behavior per house style — CASCADE for
   org, RESTRICT/NO ACTION for the rest unless a sibling precedent says otherwise; verified at plan time.)
3. Indexes on `organization_id`, `user_id`, `vacancy_id`; UNIQUE on `offer_id`.
4. **RLS in the same migration** (do not repeat 1.5's miss): `ENABLE` + `FORCE ROW LEVEL SECURITY` + the
   fail-closed `tenant_isolation` policy, byte-for-byte the pattern from
   `20260710160000_enable_rls_role_family_weight_profiles`.

Applied to prod at ship time via `psql --single-transaction` against the direct host (the established recipe —
prod is not Prisma-migrate-managed). Purely additive → applied before merge, zero downtime.

## 6. Write path

- **`packages/api/src/repositories/hire-prediction.repository.ts`**
  - `createHirePrediction(tx: PrismaTxClient, data: HirePredictionCreateData): Promise<{ id: string }>` —
    `tx.hirePrediction.create({ data, select: { id: true } })`. Accepts the transaction client so it runs
    inside the caller's `$transaction`.
- **`packages/api/src/repositories/fit-engine.repository.ts`** (extend)
  - `getFullFitScoreForSnapshot(tx, orgId, candidateId, vacancyId): Promise<FullFitScore | null>` — a read
    returning `{ overallScore, breakdown, weights, isPartial, calculatedAt }` (the existing
    `getFitScoreForExplain` omits `weights/isPartial/calculatedAt`). Uses the tx client for a consistent read
    inside the hire transaction.
- **`packages/api/src/services/hire-prediction.service.ts`**
  - `buildHirePredictionSnapshot(input): HirePredictionCreateData` — **pure function**. Given the
    fetched-or-null full FitScore plus `{ organizationId, userId, candidateId, vacancyId, offerId,
    applicationId, hiredById }`, returns the create-data and computes `predictionStatus`. Null/partial
    tolerant. No I/O.
  - `captureHirePrediction(tx, ctx, { offer, newUserId }): Promise<void>` — reads the full FitScore via the
    repo (tx), calls `buildHirePredictionSnapshot`, then `createHirePrediction` (tx).
- **Wire into `convertToEmployee`** (`offer/lifecycle.ts`), inside the existing `db.$transaction`, **after**
  `tx.user.create` (needs `newUser.id`): call `captureHirePrediction(tx, ctx, { offer, newUserId: newUser.id })`.
  No other change to the conversion logic.

Order inside the tx: create User → create OnboardingPlan → (optional UserTeam) → update Offer status →
**capture HirePrediction** (any position after user create is fine; place after the existing writes to
minimize diff). All atomic.

## 7. Edge cases

- **No FitScore** → `predictionStatus: 'none'`, all snapshot fields null; row still created.
- **Partial FitScore** → `predictionStatus: 'partial'`, fields populated from the partial score.
- **`applicationId` null** → stored as null (nullable column).
- **Double conversion** → already blocked upstream (`convertToEmployee` throws CONFLICT if a User with the
  email exists, and flips Offer→converted); the `@unique(offerId)` is a belt-and-suspenders DB guard.
- **Immutability** → the row is never updated after creation; no update path is built.

## 8. Security

- Write inherits the existing `permissionProcedure('offer','create')` gate on `convertToEmployee`.
- New table is org-scoped: `organization_id` + `tenant_isolation` RLS (fail-closed), enforced via `tenantDb`.
- No PII beyond FK ids + numeric scores/breakdown; no free-text candidate PII stored in the snapshot.
- Explicit `select` on the repository create (returns only `id`).

## 9. Testing

- **Pure builder unit tests** (`buildHirePredictionSnapshot`): scored / partial / none cases; correct
  `predictionStatus`; null `applicationId`; null-tolerance; frozen fields copied exactly from the FitScore.
- **Repository test** (mock/dmmf-based per CI reality — no live DB): `createHirePrediction` issues the correct
  `create` shape; `getFullFitScoreForSnapshot` selects the full field set.
- **`convertToEmployee` integration tests** (mock tx): a HirePrediction is created for a scored hire and for a
  no-score hire; correct field mapping; the create runs inside the same tx (rolls back with the hire on
  failure).
- **Full local gate:** `prisma generate` → api `tsc` → web `tsc` → `npx vitest run`. No new user-facing
  strings, so the i18n gate needs no new keys (verify it still passes).

## 10. Scope boundary (explicitly NOT in this sprint)

- No analyst UI, no tRPC read query for predictions (Phase 2 tool-26).
- No refactor of `convertToEmployee` into a service layer (existing tech debt, left as-is by decision).
- No Prisma relation fields on core models (scalar FKs only).
- No backfill of predictions for already-converted offers (only new conversions are captured; historical
  hires predate the FIT engine anyway).
