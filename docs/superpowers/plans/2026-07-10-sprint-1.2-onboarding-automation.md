# Sprint 1.2 — New-Org Onboarding Automation Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development
> (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use
> checkbox (`- [ ]`) syntax for tracking.

**Goal:** A brand-new org isn't forced through manual CRUD screens or silently blocked on
entitlements before it can do anything, and a first-login admin sees a concrete "what to do
first" checklist instead of an empty-metrics dashboard. Closes Sprint 1.2 (1.2.a/1.2.b/1.2.c) of
the TIMS ATS master build plan.

**Architecture:** Extends the TWO existing org-creation transactions (self-serve signup in
`apps/web/app/auth/callback/route.ts`, platform-owner-provisioned in
`packages/api/src/routers/platform/organizations.ts`'s `createOrganization`) with 3 more creates
in the SAME `$transaction` — no new architecture, this mirrors the exact pattern
`packages/db/prisma/seed-entitlements.ts`'s `provisionInvu` already uses for entitlement
provisioning. One new lightweight query (`organization.getSetupStatus`), one new dismiss
mutation, one small new settings page (branding — none exists today, confirmed by grep), and one
new dashboard widget. No service layer introduced — `organization.ts`/`platform/organizations.ts`
call `tenantDb`/`db` directly today, follow that existing convention.

**Tech Stack:** Next.js 15 App Router, tRPC, Prisma (`tenantDb` for tenant routers, privileged
`db` for the platform router — match each file's existing client, do not swap them), Vitest
(`environment: 'node'`, no React render harness in this repo — UI wiring is verified by the
acceptance criteria's live click-through, not a new test framework).

## Global Constraints

- Both org-creation transactions must get the SAME 3 additions (Company+BusinessUnit+Team,
  entitlements bundle) — do not fix only one and call it done. `auth/callback/route.ts` uses the
  privileged `db` import (no tenant context exists yet during signup — the org doesn't exist
  until the transaction commits); `platform/organizations.ts` also uses privileged `db`
  (`platformProcedure`). Neither goes through `tenantDb` — do not change that, it would break (no
  org id to scope on yet).
- Entitlements bundle applies to the org regardless of its legacy `OrgPlan` enum value (trial/
  starter/professional/enterprise) — this matches the existing `provisionInvu` precedent (INVU is
  `professional` but still gets the full `ats-base` bundle). Do NOT restrict to `trial` only; the
  `OrgEntitlement` rows use `source: 'plan'` and remain fully operator-editable afterward via the
  existing platform entitlements admin UI (Company Entitlements feature, already live) — this is
  a sane starter default, not a lock-in.
- `Company.country` is a required field with NO db default (`country String` in
  `organization.prisma:66`, no `@default`). Default to `'CO'` in code for auto-created companies
  (editable immediately via existing Settings) — this matches the schema's own existing defaults
  elsewhere (`timezone: "America/Bogota"`, `language: "es"`), which are already Colombia-centric.
- i18n: new UI text needs keys in BOTH `apps/web/lib/i18n/es.json` AND `apps/web/lib/i18n/en.json`.
- No `any` type. Prisma queries use explicit `select` (never a full-record return) — CLAUDE.md.
- Multi-step DB writes wrap in `db.$transaction` (`.claude/rules/db.md`) — both signup paths
  ALREADY use `$transaction`; add the new creates INSIDE the existing transaction, do not open a
  second one.
- Schema changes: dev-only via `cd packages/db && npx prisma db push --schema=prisma/schema`,
  then `npx prisma generate --schema=prisma/schema`. Production uses `prisma migrate deploy` (not
  this plan's concern to run, but generate a real migration file, don't just `db push` and forget).
- Test convention observed in this repo: `vi.mock('@tims/db', () => ({ tenantDb: {...}, db: {...},
  runWithTenant: ... }))` + `createCallerFactory` from `packages/api/src/trpc` to invoke a router
  procedure directly (see `tests/vacancy/create-autopublish.test.ts` for the canonical tenant-side
  example; for the platform-side `db` client, mock `{ db: {...} }` instead of `tenantDb`).

  callable from both call sites, and unit-test THAT helper directly with a mocked `tx`, avoiding
  duplicated logic AND duplicated tests across the two entry points)

**Interfaces:**
- New shared helper: `packages/api/src/services/org-provisioning.ts` exporting
  `provisionOrgDefaults(tx: PrismaTransactionClient, orgId: string, companyName: string):
  Promise<{ companyId: string; businessUnitId: string; teamId: string }>` — creates, in order:
  1. `tx.company.create({ data: { organizationId: orgId, name: companyName, country: 'CO' } })`
  2. `tx.businessUnit.create({ data: { organizationId: orgId, companyId: company.id, name: 'General' } })`
  3. `tx.team.create({ data: { organizationId: orgId, businessUnitId: businessUnit.id, name: 'Equipo General' } })`
  Returns the 3 new ids (callers don't currently need them, but the platform-owner path may want
  to log them — return for future use, do not thread through if truly unused, check).
- New shared helper: `packages/api/src/services/org-provisioning.ts` also exports
  `provisionOrgEntitlements(tx: PrismaTransactionClient, orgId: string): Promise<void>` — mirrors
  `provisionInvu`'s pattern exactly: `tx.planModule.findMany({ where: { planCode: 'ats-base' } })`
  then for each, `tx.orgEntitlement.create({ data: { organizationId: orgId, moduleCode:
  pm.moduleCode, enabled: true, source: 'plan', limit: pm.limit } })` (plain `create`, not
  `upsert` — this is a first-time provisioning inside a brand-new org's own creation transaction,
  there is no pre-existing row to conflict with, unlike `provisionInvu`'s idempotent re-seed
  case). Do NOT enable any `addon`-kind module (`ai_voice_interview`, `video_interviews`,
  `proctoring`, `custom_reports`) — the `ats-base` `PlanModule` set already excludes these by
  construction (confirm by reading `ATS_BASE_MODULES` in `seed-entitlements.ts`), so simply
  iterating `planModule.findMany({ where: { planCode: 'ats-base' } })` is correct and sufficient;
  do not add extra filtering logic that would be redundant.
- `PrismaTransactionClient` type: check how the two existing call sites type their `tx` parameter
  (`db.$transaction(async (tx) => {...})` — infer from `Prisma.TransactionClient` if that's the
  existing convention in this codebase, e.g. check `provisionInvu`'s signature in
  `seed-entitlements.ts`) — match the existing type import path, do not invent a new one.
- Both call sites invoke `await provisionOrgDefaults(tx, org.id, org.name)` then `await
  provisionOrgEntitlements(tx, org.id)` right after `org` is created (order matters: FK
  dependency), before the transaction's remaining creates (role/user/subscription).

### Task 2: `organization.getSetupStatus` query + per-user dismiss

**Files:**
- Modify: `packages/db/prisma/schema/user.prisma` (add one nullable field to `User`)
- Modify: `packages/api/src/routers/organization.ts` (add 2 procedures)
- Test: `tests/organization/setup-status.test.ts` (new)

**Interfaces:**
- Schema: add `setupChecklistDismissedAt DateTime? @map("setup_checklist_dismissed_at")` to
  `User` (`packages/db/prisma/schema/user.prisma`) — small additive nullable column, no migration
  risk. Run `prisma db push`/`generate` per Global Constraints.
- New query `organization.getSetupStatus: permissionProcedure('organization', 'read').query(...)`
  returning:
  ```ts
  {
    items: {
      companyStructureReady: boolean;   // always true (post Task 1, every org has one at creation)
      teamInvited: boolean;             // db.user.count({ organizationId }) > 1
      brandingSet: boolean;             // db.organization.findUnique({ select: { logo: true } })?.logo != null (see Task 3)
      firstVacancyPosted: boolean;      // db.vacancy.count({ organizationId, deletedAt: null }) > 0
      firstVacancyPublished: boolean;   // db.vacancy.count({ organizationId, status: 'published', deletedAt: null }) > 0
    };
    allComplete: boolean;               // all 5 items true
    dismissedAt: string | null;         // ctx.user's own setupChecklistDismissedAt (ISO string), null if never dismissed
  }
  ```
  Run the 4 live `count`/`findUnique` checks via `Promise.all` (cheap parallel queries, short-TTL
  cache per this repo's caching conventions if a convenient existing helper applies — check
  `packages/api/src/lib/cache.ts`'s `cacheGet`/`cacheSet`, TTL ~60s, key
  `tims:setup-status:{orgId}`; skip caching if it adds meaningful complexity for a query this
  cheap — your call, but don't invent a new caching pattern, reuse the existing helper if used at
  all).
- New mutation `organization.dismissSetupChecklist: permissionProcedure('organization',
  'update').mutation(...)` — sets `ctx.user`'s OWN `setupChecklistDismissedAt = new Date()` (not
  an org-wide setting — per-user, per spec). Note: dismissal auto-re-shows after 7 days if still
  incomplete — implement this as a check in `getSetupStatus` itself (if `dismissedAt` is set AND
  `Date.now() - dismissedAt > 7 days` AND `!allComplete`, return `dismissedAt: null` to the
  frontend so the widget re-shows, without mutating the stored value — simplest correct
  interpretation, avoids a background job for something this small).

- [ ] **Step 1: Add the schema field, `prisma db push` + `generate`.**
- [ ] **Step 2: Write the failing test** for `getSetupStatus` (all 5 items false for a fresh org
  with only the auto-created company/unit/team from Task 1 → `companyStructureReady: true`,
  everything else false; each item flips true under its respective condition; the 7-day
  re-show logic) and `dismissSetupChecklist` (sets the caller's own field, not another user's).
- [ ] **Step 3: Implement both procedures.**

## Acceptance criteria (whole sprint)

- Sign up as a new company account → land on a dashboard with a Setup Checklist showing item 1
  ("company structure ready") already checked, without touching Settings first; a Company +
  BusinessUnit + Team already exist to assign a vacancy to.
- The new org's entitlements immediately unblock vacancies/candidate-portal/ai-screening/
  compliance-matrix/assessments/interviews/validations (the `ats-base` set) with zero
  platform-owner intervention; addon-gated features (`ai_voice_interview` etc.) correctly show as
  not-enabled/upsell-gated, unchanged.
- Completing checklist items 2 (invite a teammate) and 4/5 (post + publish a vacancy — Sprint 1.1
  dependency, already shipped) causes the checklist to reflect completion without a page reload
  beyond normal query invalidation.
- The platform-owner-provisioned enterprise path (`create-org-modal.tsx` →
  `platform.createOrganization`) gets the SAME defaults — not left as a documented gap.
