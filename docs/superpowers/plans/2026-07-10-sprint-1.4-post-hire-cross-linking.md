# Sprint 1.4 — Post-Hire Workflow Cross-Linking Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development
> (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use
> checkbox (`- [ ]`) syntax for tracking.

**Goal:** Cross-link 4 post-hire modules that today compute real data but never surface it to each
other: a Nine Box "star"/"high_potential" placement becomes a one-click suggested successor; the
already-built-but-frontend-unused `getLowProgressAlerts` endpoint becomes visible; overdue Climate
ActionPlans surface on the exec Monitoring dashboard; and a successor whose comp is well below
their target role's band gets flagged.

**Architecture:** No new architecture. All 4 tasks are read-mostly query additions + frontend
wiring on top of already-correct backend data — this is explicitly the "cheapest fix in the whole
plan" category of work (per the master build plan's own framing of 1.4.b). Two tasks (1.4.a,
1.4.d) needed real-code research before this plan could be written accurately — see the "Scope
corrections" note in each task below; both were originally scoped assuming an existing form/flow
that a verification pass found does NOT exist, so both are narrowed to avoid silently inventing a
larger feature (a full CriticalRole CRUD UI, a full salary-adjustment-request page) than this
sprint's stated goal calls for.

**Tech Stack:** Next.js 15 App Router client components, tRPC, Prisma (`tenantDb`), Vitest
(`environment: 'node'`, no React render harness — pure/extractable logic gets a real unit test,
JSX wiring is verified by live click-through).

## Global Constraints

- i18n: new UI text needs keys in BOTH `apps/web/lib/i18n/es.json` AND `apps/web/lib/i18n/en.json`.
- No `any` type. Prisma queries use explicit `select`.
- Schema changes (Task 4 only): dev via `prisma db push` + `generate`; hand-author a production
  migration SQL file matching this repo's existing convention (see
  `packages/db/prisma/migrations/20260710000000_add_user_setup_checklist_dismissed_at/`).
- **Task 1 (Nine Box → Succession) is suggestion-only** — never auto-creates a `Successor` row.
  The human clicks "Add as successor," pre-filled but editable before confirming. This is a hard
  constraint, not a style choice: HR decisions stay human-authored.
- Test convention: `vi.mock('@tims/db', () => ({ tenantDb: {...} }))` + `createCallerFactory` from
  `packages/api/src/trpc` (see `tests/vacancy/create-autopublish.test.ts` for the canonical
  example). Pure logic gets a plain Vitest unit test with no mocking.

### Task 1: Nine Box → Succession suggested-successor query

**Files:**
- Modify: `packages/api/src/routers/succession.ts` (new `getSuggestedSuccessors` query)
- Modify: `apps/web/app/(admin)/talent/succession/page.tsx` (new "Suggested" section)
- Test: new file, e.g. `tests/succession/suggested-successors.test.ts`

**Interfaces:**
- New query `succession.getSuggestedSuccessors({ criticalRoleId: z.string().uuid() })`
  (`permissionProcedure('succession', 'read')` — match the existing procedure-gating convention
  already used by the sibling queries in this router, e.g. `getFlightRisk`/`getRolesWithoutSuccessor`):
  finds the most-recent-period `NineBoxEvaluation` rows where `quadrant IN ('star', 'high_potential')`,
  excludes any user already a `Successor` for this `criticalRoleId` (via the confirmed
  `@@unique([criticalRoleId, userId])` constraint — a simple `NOT IN` subquery or a `where: {
  successors: { none: { criticalRoleId } } }` relation filter, whichever matches this codebase's
  existing query style for similar exclusion checks), ordered by potential/performance score
  (check `NineBoxEvaluation`'s actual scoring fields — the model wasn't fully read in this
  session's research beyond `quadrant`; read it fully at implementation time). Maps
  `quadrant === 'star' → suggested readiness 'ready_now'`, `quadrant === 'high_potential' →
  suggested readiness 'ready_1_year'` (confirmed via research: `Successor.readiness` is a real
  field — check its exact enum/string values before mapping to them). This is a documented
  starting heuristic (say so in a code comment), not a hard rule.
- Frontend: a "Suggested" section on the Succession detail page (confirmed to exist at
  `apps/web/app/(admin)/talent/succession/page.tsx`), each suggested row with a one-click "Add as
  successor" that PRE-FILLS the EXISTING `add-successor-modal.tsx`'s form (confirmed at
  `apps/web/app/(admin)/talent/succession/add-successor-modal.tsx:37`,
  `trpc.succession.addSuccessor.useMutation`) rather than silently auto-submitting — the modal
  must still open with the suggested user/readiness pre-selected but require the human to confirm
  submit.

  enumerate scoring/readiness fields — verify before writing the query).
- [ ] **Step 2: Write the failing test** for `getSuggestedSuccessors`: returns star/high_potential

**Scope correction (verified this session, differs from the original spec assumption):** the
original plan assumed (a) an existing `CriticalRole` create/edit form to add the new field to, and
(b) an existing frontend "Compensation adjustment-request flow" for the comp-gap badge to link to.
**Neither exists.** Verified: `addCriticalRole` (backend mutation) has ZERO frontend callers —
there is no CriticalRole management UI in this app at all today, only a read/list view. Separately,
`createAdjustment` (`packages/api/src/routers/compensation.ts:375-403`, the mutation that actually
files a new `SalaryAdjustment` request) also has ZERO frontend callers — the only compensation UI
that exists is an APPROVE modal for already-pending requests
(`apps/web/app/(admin)/compensation/approve-adjustment-modal.tsx`). Building a full CriticalRole
CRUD UI or a full salary-adjustment-request page is real, separate scope beyond "post-hire
cross-linking" — **this task narrows to**: (a) a minimal inline control (not a new full form) on
the Succession page's existing role list to set `targetBandLevel` via a small new
single-field mutation, and (b) reusing the EXISTING (already fully built, just unwired)
`createAdjustment` backend mutation behind a minimal "Request adjustment" trigger on the comp-gap
badge — small frontend wiring of an existing endpoint, the same profile as Task 2, NOT a new
request-flow page. If a fuller CriticalRole management UI or self-serve adjustment-request page is
wanted later, that's separate, larger scope for a future sprint — flag it as such, don't build it
here.

**Interfaces:**
- `CriticalRole.targetBandLevel: String?` (soft string match to `SalaryBand.level`, confirmed to
  exist as a plain `String` field — no FK needed, matches the plan's original "soft string match"

- Comp-gap check: for each `ready_now` successor (readiness value confirmed to exist on

- Comp-gap badge on the successor row: a small "Request adjustment" action that calls the EXISTING

## Acceptance criteria (whole sprint)

- Place a user in the `star` quadrant, open a Critical Role they're not yet a successor for → they
  appear in "Suggested" with a one-click add (pre-filled, human-confirmed); an already-added
  successor never duplicates in the suggestions.
- An OKR below 30% progress and an overdue commitment both appear in the new Performance alerts
  panel (always visible, not tab-gated), each linking correctly to the underlying record (or the
  gap is flagged if no deep-link target exists).
- An overdue Climate ActionPlan appears on Monitoring; one 30 days out does not, until its due
  date moves inside the 14-day window.
- Setting a Critical Role's target band level (via the new minimal inline control, not a full new
  form) and having a `ready_now` successor well below that band's midpoint shows a correctly
  labeled comp-gap badge; clicking "Request adjustment" pre-fills and calls the existing
  `createAdjustment` mutation.
