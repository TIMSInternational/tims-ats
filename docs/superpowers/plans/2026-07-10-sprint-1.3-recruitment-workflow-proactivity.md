# Sprint 1.3 — Recruitment Workflow Proactivity Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development
> (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use
> checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make the recruitment pipeline actually proactive instead of passive: configuring a
stage's checklist finally affects candidate movement (a soft, disclosed gate — not silent), a
stage move surfaces a concrete next action instead of a bare "moved" toast, the Recruiter/Leader
nav matches the natural Vacancies→Pipeline sequence, and the vacancy-creation wizard uses the
already-built AI description generator to produce all 3 spec'd variants (formal/social/whatsapp)
plus a bias check, instead of the wizard's current plain-textarea-only Step 2.

**Architecture:** No new architecture. Task 1 adds one new `Json?` column
(`Application.checklistProgress`) plus one new mutation on the existing pipeline router/service,
and changes `moveCandidate`'s return shape (adds an optional `warnings` array — additive, does not
break existing callers that ignore it). Task 2 adds one new pure mapping file plus extends the
existing shared toast primitive with an optional action button (the ONLY existing toast callers
today are plain-text; this is a strictly additive prop). Task 3 is a 2-line nav-array swap. Task 4
extends the existing `vacancy-writer` AI agent's output schema (one Bedrock call, no new
integration) plus 2 new nullable `Vacancy` columns and wires the already-built-but-frontend-unused
`checkInclusiveLanguage` agent into the same wizard step.

**Tech Stack:** Next.js 15 App Router client components, tRPC, Prisma (`tenantDb`), AWS Bedrock via
the existing `packages/ai` agent pattern, Vitest (`environment: 'node'` — no React render harness
in this repo; pure/extractable logic gets a real unit test, JSX wiring is verified by the
acceptance criteria's live click-through).

## Global Constraints

- i18n: new UI text needs keys in BOTH `apps/web/lib/i18n/es.json` AND `apps/web/lib/i18n/en.json`.
- No `any` type. Prisma queries use explicit `select` (never a full-record return) — CLAUDE.md.
- Multi-step DB writes wrap in `db.$transaction` (`.claude/rules/db.md`).
- Schema changes: dev via `cd packages/db && npx prisma db push --schema=prisma/schema` then
  `npx prisma generate --schema=prisma/schema`; also write a real migration SQL file for
  production (this repo's migrations are hand-authored, not auto-generated by `db push` — see
  `packages/db/prisma/migrations/20260710000000_add_user_setup_checklist_dismissed_at/` for the
  exact convention to match).
- **Task 1's gate is SOFT, not hard** (deliberate, spec-deviation already accepted in the master
  build plan): `moveCandidate` must still SUCCEED when checklist items are incomplete — it returns
  a warning, never throws for this reason. Do not make it a hard block.
- **Task 2's next-action mapping is heuristic, not exhaustive** (stage names are user-configurable
  per org): match a `stageType` field if the `PipelineStage` model has one (verify first), else
  fuzzy-match the stage `name` string against the spec's canonical stage names
  (Postulado→Preselección→Evaluaciones→Entrevistas→Oferta→Contratado), with a graceful no-op
  (bare toast, today's exact behavior) for anything unmatched. Never throw or show a broken toast
  for a custom/unrecognized stage name.
- Test convention: `vi.mock('@tims/db', () => ({ tenantDb: {...} }))` + `createCallerFactory` from
  `packages/api/src/trpc` to invoke a router procedure directly (see
  `tests/vacancy/create-autopublish.test.ts` for the canonical example). Pure, React-free helper
  functions get a plain Vitest unit test with no mocking.

### Task 1: Real (soft) checklist gate on pipeline stage moves

**Files:**
- Modify: `packages/db/prisma/schema/pipeline.prisma` (`Application` model — add
  `checklistProgress Json?`)
- New migration file under `packages/db/prisma/migrations/`
- Modify: `packages/api/src/services/pipeline.service.ts` (`moveCandidate`, ~line 34-42)
- New mutation: `packages/api/src/routers/pipeline.ts` (or wherever the pipeline router lives —
  find it first) — `updateApplicationChecklist({applicationId, stageId, itemKey, completed})`
- Test: new file under `tests/pipeline/` covering both the soft-gate warning and the new mutation

**Interfaces:**
- `Application.checklistProgress: Json?` — shape:
  `Record<stageId, Record<itemKey, { completed: boolean; completedBy: string; completedAt: string }>>`.
  Only write the CURRENT stage's progress map; do not need to pre-populate other stages.
- `moveCandidate`'s return type gains an optional `warnings?: string[]` field (list of incomplete
  checklist-item labels for the stage being LEFT, not the destination — the gate checks whether
  the candidate is leaving a stage with an incomplete checklist, matching "configuring a stage's
  checklist actually affects candidate movement" — i.e. it's the SOURCE stage's checklist that
  must be satisfied before moving on, not the destination's). If the source stage has no
  `checklist` (null) or all items are marked complete in `checklistProgress`, `warnings` is
  omitted/empty and behavior is unchanged from today.
- New mutation `updateApplicationChecklist` — validates `applicationId` is in-org/in-scope (use the
  same `assertScoped`/`scopeWhereFor('application', ...)` pattern this router likely already uses
  elsewhere — check), then upserts one entry in `checklistProgress[stageId][itemKey]`.

- [ ] **Step 1: Write the failing test for the soft-gate behavior.** Cover: (a) moving from a
  stage with NO checklist → no warnings, unchanged behavior; (b) moving from a stage WITH a
  checklist where progress is empty/incomplete → `moved: true` (the application actually moves,
  confirm the underlying repository call still happens) AND `warnings` names the incomplete
  item(s); (c) moving from a stage where all checklist items are marked complete in
  `checklistProgress` → no warnings. Also test `updateApplicationChecklist` marks one item
  complete and that a SECOND call for a different item doesn't clobber the first (the progress map
  accumulates, not overwrites).

- [ ] **Step 2: Schema migration.** Add `checklistProgress Json?` to `Application`, `db push` +
  `generate` + hand-author the production migration SQL.

- [ ] **Step 3: Implement the soft gate in `moveCandidate`.** Read the SOURCE stage's `checklist`
  (Json shape — read `PipelineStage.checklist`'s actual current shape/usage first, e.g. via
  `getStageChecklist`/`updateChecklist` in the same service file, to match its item-key
  convention), compare against `application.checklistProgress[sourceStageId]`, compute
  `warnings`. Do NOT throw — always let the move proceed.

- [ ] **Step 4: Implement `updateApplicationChecklist` mutation.**

- [ ] **Step 5: Frontend wiring** — the candidate's Kanban-card detail view (find it: likely
  `apps/web/app/(admin)/recruitment/pipeline/` — a card/detail component) gets checkboxes for the
  current stage's checklist items, calling the new mutation. The pipeline page's existing
  `moveCandidate` `onSuccess` handler (currently a bare success toast, `pipeline/page.tsx:76`) reads
  `warnings` from the mutation result and shows them — this can be a simple extension of the
  existing toast call for now (Task 2 below builds the richer action-toast primitive this can
  later use; don't block Task 1 on Task 2 — a plain warning toast naming the incomplete items is a
  complete, correct Task-1 deliverable on its own).

- [ ] **Step 6: Run tests + both tsc checks.**

### Task 2: Proactive next-action toast on stage move + toast primitive extension

**Files:**
- Modify: `apps/web/lib/toast.ts` (add an optional action button)
- New: `apps/web/lib/pipeline-next-actions.ts` (pure mapping, stage → suggested action)
- Test: new file, e.g. `tests/pipeline/pipeline-next-actions.test.ts`
- Modify: `apps/web/app/(admin)/recruitment/pipeline/page.tsx` (~line 76, the move-success toast)
- Modify: i18n files

**Interfaces:**
- `toast(message: string, options?: ToastOptions)` gains an optional
  `action?: { label: string; href: string }` in `ToastOptions`. When present, render a clickable
  link inside the toast alongside the message (read `apps/web/lib/toast.ts`'s current DOM-building
  code first — it currently does `el.textContent = message`; this needs to become structured DOM
  construction, e.g. a message span + an anchor, NOT innerHTML with unsanitized input — message and
  the action label/href are always internal strings, never raw user input, so this is safe, but
  keep the construction explicit createElement-based to match this file's existing vanilla-DOM
  style, don't introduce a new dependency).
- `pipeline-next-actions.ts` exports a pure function, e.g.
  `getNextActionForStage(stageName: string, stageType?: string | null): { labelKey: string; href: string } | null`
  — matches the spec's canonical stage sequence
  (Postulado→Preselección→Evaluaciones→Entrevistas→Oferta→Contratado) either via a `stageType`
  field (verify first whether `PipelineStage` has one) or fuzzy name-matching (case-insensitive,
  accent-insensitive since these are Spanish names), returns `null` for unmatched/custom stages.

- [ ] **Step 1: Verify whether `PipelineStage` has a `stageType`/`type` field** (read the model).
  If yes, match on it (exact, most reliable). If no, implement fuzzy name matching (normalize
  accents/case, match against the 6 canonical Spanish stage names) — write this decision into the
  function's doc comment either way, since a future stage-name change could silently break fuzzy
  matching and a maintainer should know why.
- [ ] **Step 2: Write the failing test for `getNextActionForStage`** — one case per canonical
  stage name, one case for an unrecognized custom name (returns `null`), one case exercising
  whatever matching strategy Step 1 settled on.
- [ ] **Step 3: Implement `getNextActionForStage`.**
- [ ] **Step 4: Extend `toast.ts`** with the optional `action` prop, rendering a real clickable
  link/button. Existing callers (bare-message toasts) remain unaffected — this must be additive.
- [ ] **Step 5: Wire into `pipeline/page.tsx`'s move-success handler** — after a successful move,
  look up the next action for the DESTINATION stage (not the source — this is forward-looking
  guidance, distinct from Task 1's backward-looking checklist warning) and pass it as the toast's
  `action`. Both Task 1's warnings and Task 2's next-action toast can coexist in the same
  `onSuccess` handler (they answer different questions: "did I leave anything undone" vs "what
  should I do now").
- [ ] **Step 6: i18n keys for the "Evaluaciones→Assign the assessment battery now"-style action
  labels** (one per canonical stage) in both `es.json`/`en.json`.
- [ ] **Step 7: Run tests + both tsc checks.**

## Acceptance criteria (whole sprint)

- Configure a stage's checklist with 2 items → move a candidate out of it without completing
  either → a warning names the incomplete items, the move still succeeds. Mark both complete →
  move a different candidate → no warning.
- Move a candidate into a stage matching "Evaluaciones" → the success toast includes an actionable
  next-step link. Move into an unrecognized custom stage name → graceful plain-toast fallback,
  never a broken/blank action.
- Recruiter and Leader nav both show Vacancies above Pipeline.
- In the vacancy-creation wizard, clicking "Generate with AI" with a title filled produces 3
  distinct variants (formal longest/structured, social shorter, whatsapp shortest/plain-text),
  each individually usable; the chosen formal variant's description lands in `Vacancy.description`
  on save. The inclusive-language check runs against the current description text and shows a
  score + suggestions.
