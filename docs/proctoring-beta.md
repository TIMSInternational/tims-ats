# Proctoring beta: behavior and verification

The proctoring slice is an **opt-in, advisory review workflow** for timed candidate assessments. It does not determine identity or misconduct. Its signals must be interpreted by a person alongside the assessment and any candidate explanation. Do not market it as SMOWL-equivalent or assign an accuracy percentage until the device and demographic validation below is complete.

## End-to-end contract

1. A super admin or tenant-bound platform owner enables proctoring for an assessment type, if the organization has the `proctoring` entitlement. The assignment snapshots `proctoringRequired`; changing a type only affects future assignments. Existing assignments are unproctored unless they were already assigned under an enabled policy. An audited pre-start accommodation may turn this snapshot off for one assignment.
2. The browser first checks the live .NET 10 proctoring capability flag. Only when it is enabled does a candidate see assessment, camera, and screen-monitoring consent separately. The browser opens a camera preview and asks the candidate to share the **entire display**. The preflight checks a live video track and three fresh frames with exactly one detected face. Permission denial, a non-display share, or unavailable detection keeps the assessment from starting.
   If a candidate cannot pass this gate, an authorized staff member can grant an audited, reason-coded accommodation on an **assigned, not yet started** assessment. That assignment then uses the ordinary unmonitored assessment path; the assessment type policy and other assignments are unchanged.
3. Only after preflight does the .NET 10 `POST /candidate/{orgSlug}/assessments/{assignmentId}/proctoring/start` route atomically record consent, start the assessment timer, and create/resume one session. A resumed assessment keeps its original start time. The ordinary TypeScript `startAssessment` endpoint rejects proctored assignments.
4. While the questions are open, the browser samples an on-device MediaPipe face detector at most once per second. Three consecutive no-face or multiple-face samples emit a bounded, idempotent observation. Tab visibility, window focus, camera, and screen-track loss also emit observations. The client sends a heartbeat every 30 seconds; a server-observed gap over 90 seconds becomes its own event. The candidate can reconnect either stream without resetting the timer. After answer submission, the client gives pending observations up to two seconds to sync before calling completion; missing observations still cannot be treated as proof of continuous monitoring.
5. Assessment submission still commits through the existing TypeScript service. The candidate then calls the .NET 10 `/complete` route, which closes the proctoring session only after the assignment is completed. If that second call is lost, the staff queue and evidence routes reconcile completed assignments to their sessions before presenting review data. This is an idempotent repair, **not** one atomic cross-service transaction. Active sessions with no heartbeat for over three minutes appear as `needs_attention` in the staff queue but remain resumable; a final decision is allowed only after submission. HR admins and HRBPs may inspect scoped, paginated evidence; recruiters and leaders have no integrity-evidence access. Only super admins and tenant-bound platform owners may record `clear`, `concern`, or `inconclusive` decisions with notes. Evidence is classified as restricted and read/review actions are audited. No flag automatically fails an assessment.

Only event metadata is stored: type, severity, server receipt time, optional client time, and a source marker. Camera frames, screen pixels, audio, face landmarks, and embeddings are not uploaded or stored. The server derives severity and does not trust the client clock or a client-supplied misconduct verdict. Browser-provided capability booleans, heartbeats, and observations are **not attestation**: a candidate can modify or suppress them outside the app. Missing monitoring is a human-review cue, not an automatic fail.

An already-started assessment can submit during a two-minute grace period after the earlier of its assignment expiry or duration deadline. The server applies that bound again inside its write transaction, allowing the browser countdown to auto-submit at 0:00 without accepting an unlimited late attempt. The cross-stack submission and .NET session-close steps remain separately retried/reconciled.

The platform-owner access export includes bounded proctoring consent, session, human-review, and event metadata with per-record fail-closed audit. It marks capped data and legacy free-text event JSON for manual follow-up rather than presenting a partial export as complete. Automated retention/erasure is still pending an approved retention policy.

## Verification matrix

| Layer | Required checks |
| --- | --- |
| API/service | Tenant and candidate ownership; entitlement and policy snapshot; consent; one session on concurrent starts; stable timer on resume; bounded/idempotent events; review authorization and notes; event pagination; completed-only review; pre-start accommodation scope, race, and audit. |
| Database | Apply migration twice on a disposable PostgreSQL database; verify `app_tenant` can insert/read own events, cannot update/delete, cannot read other tenants, and cannot attach an event to another tenant's session. |
| Browser automation | Permission denied; camera lost; window-only share refused; preflight remains gated when the model is unavailable or face count is not one; timing and retry; event delivery/heartbeat; submission and reviewer queue. Use fake media for deterministic tests. |
| Real devices | On every supported OS/browser, test a real camera and full-display chooser, pause/stop capture, device unplug, reload, offline/reconnect, poor light, glasses/occlusion, more than one person, and a long exam. Confirm the screen/camera indicator and candidate recovery copy. |
| Accuracy | Collect **consented, representative, labeled** clips for the intended devices, lighting, skin tones, face coverings, and seating positions. Separately report false alarms and missed detections for one face, no face, and multiple faces, with confidence intervals. Include failure-to-initialize and camera-frame stalls as unavailable, not as absence. Review subgroup performance and thresholds before customer use. |

Automated tests and a synthetic webcam exercise verify wiring and basic detection, **not** real-world accuracy. The MediaPipe BlazeFace model card excludes identity recognition and surveillance from its intended uses; TIMS uses it only as a candidate-visible, on-device face-presence cue. A browser page also cannot inspect a second device or guarantee that screen sharing remains genuine. These limits must be explained to pilot customers.

## Release conditions

- Approve candidate-facing assessment/proctoring notice, consent text, and a defined event retention period. The platform-wide retention/erasure workflow is still open; implement an audited purge for these events before onboarding external candidates. The bounded, audited DSAR metadata export already exists, but capped or legacy content requires manual fulfillment. Raw-media storage is deliberately absent pending a separate privacy and retention decision.
- Complete the real-device matrix and labeled accuracy study. Set support and escalation policy for candidates unable to provide camera/full-display access or for model failures; the audited pre-start accommodation route supports an unmonitored assessment after staff approval. Use human review only; never automatically reject from a face signal.
- Apply and verify the new database migration on staging, enable the entitlement only for a test organization, run a full candidate-to-reviewer dry run, and monitor failed starts, model initialization, event sync, heartbeat gaps, and reviewer workload before broader activation.
- Deploy the .NET 10 service with the Prisma migration before setting `Platform:ProctoringEnabled=true`; the flag defaults to false. Keep the entitlement off except for a consented test organization until the release conditions above pass. Prisma continues to own the assessment DDL, while the direct .NET routes own proctoring session/event and reviewer behavior. The older assessment authoring/submission routes remain until the broader assessment-domain cutover.
