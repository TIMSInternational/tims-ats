> **Status:** plan only. Nothing in this document has been executed.

> **never read**; only names are listed.

> static-key users, IDs) on top. Whether to scrub the existing mentions is a separate decision

## 3. What each platform's transfer keeps and drops (official docs)

### 3.1 Vercel project transfer — https://vercel.com/docs/projects/transferring-projects (last updated 2026-09-08)

- "transfer projects between your Vercel teams with **zero downtime**". You must be an **owner of the source team and a member of the target team**. The target team needs a valid payment method.
- **Consequence for rollback:** after the move, the source of a transfer back is the TIMS team, so undoing it needs an **Owner of the TIMS Vercel team** who is also a member of the NexaDev team. Member access in the TIMS team is not enough.
- **Transferred:** deployments; environment variables ("copied", except those in `vercel.json` `env`/`build.env`; verified 2026-10-12: `apps/web/vercel.json` has neither; it sets only `framework`, `buildCommand`, `regions: ["pdx1"]` and the `/api/cron/evaluate-alerts` cron at `0 6 * * *`); project configuration; domains and aliases; administrators; project name; builds; Git repository link; security settings; Cron Jobs; preview comments; Web Analytics; Speed Insights; function region.
- **Not transferred:** integrations (re-add them), usage (reset), monitoring data, runtime + build logs, custom log drains, Vercel Blob / Edge Config (separate mechanism), Secure Compute / static IPs.
- Domains: a subdomain such as `app.timsint.com` is **delegated** to the target team while the apex stays with the origin team. This is a reason to move `timsint.com` itself to the TIMS team (or to keep the ATS domain on a TIMS-owned apex).
- A transfer takes 10s–10min. During it you cannot deploy or edit settings.

### 3.2 Supabase project transfer — https://supabase.com/docs/guides/platform/project-transfer

- "freely transfer projects between different organizations". It is an org move **"without touching the infrastructure"** (https://supabase.com/docs/guides/platform/migrating-within-supabase). The project ref, URL, database, connection strings and API keys therefore stay the same. The keys staying the same is an inference from "without touching the infrastructure". The docs do not list keys explicitly: **UNVERIFIED**. Confirm by comparing `get_publishable_keys` before and after.
- **Prerequisites:** owner of the source org; at least member of the target org; **no active GitHub integration**; no project-scoped roles (Team/Enterprise); **no log drains**.
- **Consequence for rollback:** a transfer back starts from the TIMS org, so it needs an **Owner of the TIMS Supabase org** who is also a member of the NexaDev org. Being an Owner of the NexaDev org does not help once the project has left it.
- Billing: the source org pays usage and add-ons up to the transfer, the target org pays after. Credits can move between orgs via a support ticket (https://supabase.com/docs/guides/platform/billing-faq).
- Watch out for: "a short 1-2 minute downtime if you're moving a project from a paid to a Free Plan". Features can be lost on a lower plan, and the Free plan has a 2-project limit. **Upgrade the target org to Pro before the transfer.**
- It cannot change region (it stays us-west-2, which matches App Runner).

### 3.3 GitHub

- A repo transfer is **not needed**: the repo already lives in `TIMSInternational`. The task is org **ownership continuity**: https://docs.github.com/en/organizations/managing-peoples-access-to-your-organization-with-roles/maintaining-ownership-continuity-for-your-organization. "we recommend that at least two people within each organization have the owner role". You can't change your own role, so a TIMS owner demotes the NexaDev account afterwards.
- For reference only, if anyone ever proposes moving the repo (https://docs.github.com/en/repositories/creating-and-managing-repositories/transferring-a-repository): issues, PRs, wiki, stars and history move. Webhooks, secrets and deploy keys "remain associated". Redirects work until someone recreates the old name. **But** the AWS deploy role trusts `repo:TIMSInternational@305569681/tims-ats@1301900745`, which includes the immutable owner ID. **Any transfer to another owner breaks every AWS deploy and rollback until the trust policy is updated.** Do not transfer.

### 3.4 AWS (no "transfer" exists for these resources)

- The account holds other products, so it cannot be given away. Resources are rebuilt.
