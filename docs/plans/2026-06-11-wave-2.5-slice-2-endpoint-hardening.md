# Wave 2.5 Slice 2 — Endpoint Hardening: Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development
> (recommended) or superpowers:executing-plans to implement this plan task-by-task.
> Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Close the ungated-mutation holes the Wave 2.5 audit found — gate
`notification.create`/`bulkCreate` and `organization.list*` behind
`permissionProcedure`, gate + self-scope `engagement.submitSurveyResponse`, delete
the dead staff-session stubs from the portal router, and add a server-side
`/platform` layout gate so non-platform-owners are bounced before any platform page
renders.

**Architecture:** Pure consumption of the slice-1 engine — every change swaps
`protectedProcedure` for `permissionProcedure(module, action)` (which injects
`ctx.access` via `buildAccessForUser`) or deletes dead code. No new access
machinery. The `/platform` gate is a nested Next.js App Router server layout that
re-checks `isPlatformOwner` on the REAL Supabase identity (impersonation rides a
cookie, not a session swap, so the check naturally targets the operator).
Spec: `docs/WAVE-2.5-ACCESS-CONTROL.md` (slice 2 bullet).

**Tech Stack:** TypeScript strict, tRPC v11, Next.js 15 App Router server
components, Vitest (static-source assertion style used across `tests/security/`).

**Baseline (verified on branch creation):** 282 tests / 40 files, all green, on
`feat/access-endpoint-hardening` off main `815b853`.

**Recon ground truth (verified Jun 11, do not re-litigate):**
- `notification.create` (`packages/api/src/routers/notification.ts:151`) and
  `bulkCreate` (`:169`) are plain `protectedProcedure` taking arbitrary
  `userId`/`userIds` — any employee can notify anyone (phishing vector). ZERO
  client callers in `apps/web`.
- `organization.listCompanies`/`listBusinessUnits`/`listTeams` are plain
  `protectedProcedure`. ZERO client callers. `listTeams` leaks full org structure
  incl. every member's name/avatar to any staff role. `getCurrent` stays
  `protectedProcedure` (own-org lookup; design names only `list*`).
- `engagement.submitSurveyResponse` (`packages/api/src/routers/engagement.ts:110`)
  is plain `protectedProcedure`; userId already comes from ctx (good) but the
  endpoint is unguarded by module:action and `answers` is an UNBOUNDED
  `z.record` (violates CLAUDE.md input-bounds rule).
- Portal router (`packages/api/src/routers/portal.ts`): EIGHT dead
  staff-session (`protectedProcedure`) procedures with zero client callers —
  `uploadDocument`, `getMyAssessments`, `startAssessment`, `acceptOffer`,
  `declineOffer`, `updateProfile`, `requestDataDeletion`, `submitNps`. The live
  candidate flows moved to `candidatePortal` router on `candidateProcedure`
  (Wave 1 slices 1-4, ALL SHIPPED) and offer acceptance is the public
  `/offers/sign/[token]` flow. `docs/WAVE-1.5a-ASSESSMENT-PLAYER.md` slice 2
  plans to remove `getMyAssessments`/`startAssessment` itself and rebuilds
  assessment-taking on `candidateProcedure` in `candidatePortal` — removing them
  here pre-completes that step, no conflict (Task 6 updates that doc). The
  design doc names three stubs; all eight are the same dead class — removing the
  whole class is the deliberate scope decision (recorded in the PR body).
  The portal router KEEPS its four public career-site procedures
  (`getPortalStats`, `listVacancies`, `getVacancy`, `applyToVacancy`).
- Seeded matrix (`packages/db/prisma/seed-access.ts`): `notification` create =
  hr_admin/super_admin only; `organization` read = hr_admin/super_admin;
  `engagement` create = employee(own)/hr_admin/super_admin. Leader-only users
  lose survey submission — matrix-faithful; role stacking (leader+employee) is
  the designed answer.
- `/platform` pages live at `apps/web/app/(admin)/platform/*` with NO own
  layout — only the API (`platformProcedure`) blocks non-owners today; the
  pages themselves render then error.
- Deploy gate: this slice merges to main but the WAVE DOES NOT DEPLOY until
  slices 1-4 ship together. `seed-access.ts --apply` remains FORBIDDEN. The
  single DB IS prod — nothing in this plan touches the DB.

**Wave map (this plan = Slice 2 only):** 3 scope enforcement: recruitment ·
4 scope enforcement: people · 5 role-aware UI · 6 sensitive-data layer ·
7 new-role surfaces.

```typescript
import { getUser } from '@tims/auth/server';
import { redirect } from 'next/navigation';
import { db } from '@tims/db';

// Wave 2.5 slice 2 — server-side gate for the platform console. The parent
// (admin)/layout.tsx already enforces login/active/MFA; this nested layout adds
// the owner check so non-platform-owners never render a /platform page (before
// this, only platformProcedure blocked them — the page shell rendered, then
// errored). Checked against the REAL Supabase identity: impersonation rides a
// signed cookie, not a session swap, so an impersonating owner keeps access and
// a non-owner can never acquire it.
export default async function PlatformLayout({
  children,
}: {
  children: React.ReactNode;
}) {
  const supabaseUser = await getUser();
  if (!supabaseUser) redirect('/login');

  const appUser = await db.user.findUnique({
    where: { supabaseUserId: supabaseUser.id },
    select: { isPlatformOwner: true, isActive: true },
  });
  if (!appUser?.isPlatformOwner || !appUser.isActive) {
    redirect('/dashboard');
  }

  return <>{children}</>;
}
```
