## Pure kernels — golden-fixtured cross-stack

`contracts/fit-engine-fixtures/*.json` (6 files, 79 cases) were **generated by running the real TS
exports** (`computeWeightedScore`, `deriveExperienceScore`, `deriveEducationScore`,
`deriveLanguageScore`, `parseRequirements` — of these only `parseRequirements` was newly exported for this
purpose; the other four were already exported on `main`. A pure non-behavioral change either way) —
the TS is the oracle. `tests/fit-engine/kernels-fixtures.test.ts` asserts the TS side;
`Tims.UnitTests/Fixtures/FitEngineKernelsFixtureTests` asserts the C# `FitEngineKernels` against the
SAME files. Pinned semantics worth naming:

- **`JsRound` reproduces JS `Math.round` on every JSON-observable value**: half toward +∞ (−12.5 → −12) AND the
  0.49999999999999994 → 0 edge. Neither `MidpointRounding.AwayFromZero` (wrong on negative halves) nor
  `Math.Floor(x + 0.5)` (wrong on the epsilon edge) matches both; the implementation compares the
  fractional part against the true floor. `js-round.json` pins `Math.round` itself.
- Renormalization over available weights; missing weight key ⇒ 0 (`?? 0`); **all-present under all-zero
  weights ⇒ `{0, isPartial: true}`** (a TS quirk, reproduced).
- Education: keyword ladder checked highest→lowest (a combined "MBA & Bachelor" label classifies
  master); below-requirement scores against the FULL 5-level ladder.
- Languages: trailing-parenthetical proficiency stripped from BOTH sides, case-insensitive; duplicate
  required languages each count (`filter().length`).
- `parseRequirements`: lenient typeof-guarded parse; an EMPTY `requiredLanguages: []` is kept (and
  scores null downstream); an array input passes the TS `typeof === 'object'` check and still yields `{}`.

## Writes

Both upserts are raw `INSERT … ON CONFLICT DO UPDATE` on the TenantScope transaction (nine-box-vote /
fx-rate precedent). Both upserts are eligible for Prisma's native `upsert`, which is likewise a single
atomic `INSERT … ON CONFLICT` — so ATOMICITY holds in both stacks. (An earlier draft said "the same
statement"; that is unsupported from this repo — Prisma additionally emits a `WHERE` guard on the
`DO UPDATE` and a `RETURNING`, and nothing here captures its emitted SQL.) The fit_scores update path touches overallScore/breakdown/weights/isPartial/
calculatedAt/updatedAt and never organizationId/createdAt. Timestamps bind ms-truncated
Unspecified-kind `NpgsqlDbType.Timestamp` (TRAPS 10/11); jsonb binds as `NpgsqlDbType.Jsonb` strings.
`fit_scores` has no EF map in the WRITE context specifically (both its writes are raw SQL), but it IS
`ToTable`-mapped by `FitEngineReadDbContext` — and `scripts/table-ownership.mjs` matches `ToTable`
across all of `services/Tims.Platform/src` with NO per-context scoping, so BOTH new write entries are
gate-ENFORCED, not merely recorded. (An earlier draft said fit_scores had no map at all and that its
entry was therefore unenforced. False — and self-falsified: the map and that sentence landed in one
commit.) No native enum COLUMN is mapped anywhere in the slice (TRAPS 3/8 N/A). Three exist on tables this slice
maps and all three are deliberately unmapped: `ai_interview_sessions.status` (`AiInterviewStatus`) and
`.analysis_status` (`AiAnalysisStatus`), and `assessment_results.band` (`ScoreBand`).

## Before the flip — two things to decide, neither a code defect today

1. **`computeForVacancy` is unbounded sequential work** (divergence 3). Ported faithfully, but the C# shape
   makes it slower than the TS it replaces, and any `fit_engine:create` holder — recruiter and leader, not
   only admins — can start it on a high-volume vacancy. Decide before the write flag flips: bound the
   candidate list, restore bounded parallelism, or accept it with a timeout.
2. **The org predicate covers the DRIVING table only.** `GetFitScoresForVacancy` / `GetFitScoreForExplain`
   filter `fit_scores.organization_id`; the joined `candidates`/`vacancies` carry none (their read entities
   do not even map the column), and on the write side `job_profiles` / `assessment_results` are joined
   without one. This is NOT exploitable — the driving table is org-filtered and every join key is a PK or a
   unique FK, so only the same-org row is reachable, and RLS covers the joins besides. But the repository
   docblocks previously read "every query … with an explicit organizationId filter", which over-describes
   the control; they now say the driving table carries it and the joins rest on RLS + FK integrity. Worth
   knowing before anyone reasons about this surface under a degraded-RLS incident (cf. #111/#112).

   **What the cross-org tests do and do not prove, measured.** `Explain_CrossOrgCandidate_Is404`,
   `ExplainRow_CrossOrgCandidate_IsNull` and `WeightProfiles_AreOrgScoped_BothDirections` prove that
   ISOLATION HOLDS — which is the security property. They do NOT pin the explicit predicate: deleting the
   org predicate from both read queries was applied as a mutation and **all 67 integration tests still
   passed**, because `TenantScope` is opened with the SAME `organizationId` argument the filter uses, so RLS
   and the predicate can never disagree at this layer. That is a real limit of this test layer, stated rather
   than papered over — the one thing that WOULD distinguish them is asserting the generated SQL, which is not
   worth the brittleness for a redundant control. (Before this slice the list assertion could not even prove
   isolation: OrgB's bootstrap creates a second row named `Default`, and `IndexOf`-based ordering assertions
   hold with two of them. The count assertion is what closed that.)

## The FE wrapper (step 4's missing half) is NOT mechanical

All SIX procedures have live `apps/web` consumers, so unlike #81's `getUserGrowth` there is no
zero-consumer exemption anywhere:

| Procedure                       | Call sites                                                                         |
| ------------------------------- | ---------------------------------------------------------------------------------- |
| `listRoleFamilyWeightProfiles`  | `settings/fit-weights/page.tsx`, `recruitment/vacancies/[id]/role-family-card.tsx` |
| `upsertRoleFamilyWeightProfile` | `settings/fit-weights/page.tsx`                                                    |

**`explainFit` cannot be given a dual-path hook.** The C# side answers 501 by design, so a wrapper that
routed it on the flag would turn a working narrative panel into an error the moment the flag flipped.
Five hooks are dual-path-able; `explainFit` must stay on tRPC and be pinned by name as a deliberate
omission (the shape of #81's `getUserGrowth` pin, for the opposite reason — zero consumers there, an
unportable dependency here). That also means the fit-engine READ flag can never fully retire the TS
router while `explainFit` lives in it, which step 7 must account for.

## Step 5 — currently unrunnable, and what it needs

The parity registry has **no fit-engine surface**: `scripts/parity/seed.ts` seeds no `fit_engine`
grants and no fit_scores rows, so the six routes sit on the governance allowlist
(`tests/governance/parity-registry-covers-deployed-routes.test.ts`, two groups: five registrable-dark +
the 501-inexpressible explain-fit). Registration is #195-pattern **fixture-first** work, tracked on #90:

1. `seedFitEngineGrants` — copy scopes from `seed-access-matrix.ts` (hr_admin/recruiter@org, hrbp@unit,
   leader@team), never invent them. ⚠️ **Necessary but NOT sufficient for hrbp and leader.**
   `scripts/parity/seed.ts:1154` carries a **LOAD-BEARING ABSENCE** — the harness seeds no
   `user_business_units` rows — so a unit-scoped `hrbp` has no anchors and the four vacancy-scoped
   by-id routes answer **404**, which `expectedByRole: Record<string, 200 | 403>` cannot express. Either
   seed the anchors or register only the roles that can express a 200/403.
2. Seed fit_scores rows on a parity vacancy, or ranking/simulate compare empty-vs-empty (the
   vacuous-PASS trap).
3. `computeForVacancy` MUTATES fit_scores — its write-surface fixture needs a **dedicated vacancy** no
   read expectation depends on (this slice's own integration fixture hit exactly that hazard and split
   `VacRead` from `VacInTeam`).
4. Ensure each endpoint has a role that is DENIED (`surfaces.test.ts` requires one per endpoint) —
   `org_admin` supplies it for free here, being absent from `MATRIX` entirely.
5. **The code must be DEPLOYED to App Runner with the flag ON.** `cli.ts`'s `preflightSurface` probes the
   LIVE surface and `cmdVerifyWrite` fails with "the write routes do not appear MOUNTED" otherwise. This
   is the prerequisite that makes step 5 Federico-only rather than merely fixture-only, and an earlier
   draft of this list omitted it — so "then verify becomes runnable" did not follow from items 1–3.

With all five done, `verify fit-engine` / `verify-write fit-engine` become runnable, the cutover.sh rows
(already added, `parity_command=NONE`) flip to `verify`/`verify-write`, and the allowlist's five-route
group is deleted.
