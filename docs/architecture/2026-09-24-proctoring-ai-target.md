# TIMS ATS proctoring: AWS AI target architecture

**Status:** Design contract and implementation tracker, 2026-09-24. The local implementation is under verification and all production media/cloud flags remain off. This document does not authorize an accuracy claim or external activation.

**Initial beta sizing:** up to 25 simultaneous candidates, assessments up to 30 minutes, proposed seven-day media retention. Monthly assessment volume is pending confirmation.
**Decision:** Keep the .NET 10 API as the authorization, consent, assessment, evidence, and review authority. Add limited, consented AWS evidence capture and a separately deployed, on-demand Python inference worker. Use a pinned Hugging Face object-detection model only after a TIMS-specific evaluation. Never infer misconduct or fail an assessment automatically.

## Why this design

The [locked platform architecture](../TIMS%20ATS%20-%20Architecture.md) selected browser-side face detection and identified Rekognition as a possible later addition. The [approved Wave 1.5a design](../WAVE-1.5a-ASSESSMENT-PLAYER.md) deferred a fuller Wave 1.5b with webcam snapshots to S3, browser-integrity events, retention, consent, and staff review. The [authoritative C# target](2026-07-15-csharp-backend-target-architecture.md) gives business decisions to .NET and puts inference behind a separate service. The [acceptance register](../plans/2026-09-14-acceptance-register.md) also requires prompt escalation of critical proctoring events (APP-032).

Before this implementation, the local `codex/proctoring-beta` slice had consent, a one-face preflight gate, browser observations, heartbeats, tenant-scoped .NET persistence, and human review. It sent no images and had no AWS or Hugging Face inference. The screen-sharing check confirmed that an entire-display track was live; it did not inspect screen pixels. The current local changes add media capture, .NET evidence handling, inference transport, a worker, and infrastructure definitions. They are not yet deployed or validated against live AWS. `services/ai-gateway` remains only a historical plan. The Terraform module has not managed the live App Runner service, so infrastructure reconciliation is required before applying it.

MediaPipe BlazeFace remains useful as **candidate-facing camera positioning feedback**, but its [model card](https://storage.googleapis.com/mediapipe-assets/MediaPipe%20BlazeFace%20Model%20Card%20(Short%20Range).pdf) places surveillance and identity recognition outside scope. The local implementation removes its one-face assessment-entry gate and `face_missing`/`multiple_faces` browser reports. Preflight requires consent and functioning camera/display tracks, while face positioning feedback is non-blocking. Browser observations are untrusted hints and must not be the sole basis for an adverse decision. The cloud sees candidate-provided images too; AWS hosting does not authenticate the physical camera or guarantee that an image is genuine.

## Scope and boundaries

| In the first external beta | Outside this release until separately designed and validated |
| --- | --- |
| Camera and entire-display consent; clear recording indicator; accessible unmonitored accommodation path | Covert capture, microphone/audio recording, continuous video archive |
| Browser track/tab/focus signals and fast candidate feedback | Claim of tamper-proof browser attestation or second-device detection |
| Sampled camera and screen evidence, with strict rate and size limits | Continuous cloud inference on every video frame |
| Independent cloud face count; evaluated Hugging Face person/phone object-detection cues | Gaze, emotion, identity matching, or a single composite cheating score |
| Restricted human evidence review, candidate explanation, audited decision, prompt critical alerts | Automatic failure or automatic employment decision |
| Seven-day media expiry, event/decision retention defined in the notice, access export and erasure | Indefinite retention or model training on candidate media |

An AWS Rekognition Face Liveness entry check is an **optional extension**, not a substitute for monitoring throughout an assessment. It needs a separate identity/liveness purpose, consent, and validation. [AWS describes it as a short prompted selfie check](https://docs.aws.amazon.com/rekognition/latest/dg/face-liveness.html), not continuous exam analysis.

## Runtime and ownership

```text
Candidate browser (Next.js/Vercel)
  ├─ local camera guidance, tab/track monitoring, timed sample scheduler
  ├─ .NET 10 API: consent, session, upload-intent, upload-confirm, events
  └─ short-lived signed POST ──> private S3 staging key (us-west-2)
                                    │ .NET validates and conditionally seals copy
                                    v
                                private S3 sealed evidence key
                                    │ .NET outbox dispatches confirmed evidence only
                                    v
                                SQS inference queue + DLQ
                                    └─ Python Lambda container
                                        ├─ Rekognition DetectFaces
                                        └─ pinned HF object detector, CPU
                                             └─ SQS result queue + DLQ
                                                 └─ .NET result consumer
                                                     ├─ RLS-scoped findings
                                                     ├─ operational inbox alerts for browser/heartbeat signals
                                                     └─ restricted staff review
```

The **browser** does not get AWS credentials. It requests one upload intent per permitted sample from an authenticated, tenant-scoped .NET endpoint. The API creates a unique evidence ID and **staging** S3 key and signs a POST policy with a short expiry, exact key, content type, and size bound; [S3 POST policies support `content-length-range`](https://docs.aws.amazon.com/AmazonS3/latest/developerguide/sigv4-HTTPPOSTConstructPolicy.html), and the [.NET AWS SDK supports presigned POST](https://docs.aws.amazon.com/sdkfornet/v4/apidocs/items/S3/MS3CreatePresignedPostCreatePresignedPostRequest.html). The browser needs an explicit S3 CORS rule and a narrowly scoped frontend CSP `connect-src`; both are deployment-tested. After upload, the browser confirms the evidence ID. The API verifies object existence, expected key, and byte size, streams the bounded staged object to hash and inspect its magic bytes, then uses an ETag-conditional server-side copy to a **sealed key the browser cannot write**. It verifies the final object's checksum against the read bytes before dispatch. This prevents reuse of a still-valid POST from altering a confirmed image; a changed staging ETag aborts confirmation. The API records the sealed object identity, marks the evidence ready, and dispatches an inference command through a transactional outbox. S3 object-created events do **not** enqueue inference. Expired/orphaned staging objects are purged separately. Upload intent creation is rate-limited by session and tenant; client timestamps are informational, while server receipt time controls order and deadlines. The API or worker also decodes image bytes with dimension/decompression limits, because declared MIME and POST size alone do not make an image safe.

The **.NET API** remains the only component that resolves candidate identity, organization, assignment policy, consent, reviewer authorization, and review outcomes. It owns evidence/finding/alert metadata through the repository and tenant RLS pattern. New tables use Prisma-owned DDL during the current strangler phase, with explicit indexes, tenant RLS, and .NET writer ownership recorded in the table ledger; do not add an EF migration for them. The API's existing process may consume the lightweight result queue for the beta, including while new-session flags are off so in-flight jobs can finish. Use bounded concurrency, SQS visibility timeouts, DLQs, multireplica-safe idempotency, and a health metric for the last successful consume. On each result, .NET loads the evidence row by ID under tenant scope and compares sealed key/checksum, expected model revision, status, and expiry; tenant or assignment IDs in the queue message are never trusted. Result handling must be stateless so it can later move unchanged to `Tims.Workers`. The Python worker has no database credentials and cannot decide or write review outcomes. It returns a versioned, bounded command/result schema keyed by evidence ID and model revision. This is an explicit transport change from the C# target's synchronous `IInferenceClient`/HTTP call to an asynchronous SQS contract; the C# domain / polyglot inference boundary remains intact.

The **Python inference worker** is a separately deployed Lambda container in the existing AWS region. Its image contains pinned, checksum-verified model artifacts and dependencies: no runtime download from the public Hugging Face Hub and no outbound image transmission to Hugging Face. Lambda container images are [supported from ECR](https://docs.aws.amazon.com/lambda/latest/dg/images-create.html), and Lambda is [billed per request and duration](https://aws.amazon.com/lambda/pricing/), which avoids an idle GPU endpoint for a small beta. SQS concurrency is capped, failures retry with a dead-letter queue, and every result is idempotent. The worker calls pay-per-image Rekognition `DetectFaces` for a cloud-computed face count and a versioned Hugging Face model for person/phone cues. It treats low-confidence and failed inference as `unavailable`, not `clear`.

Initial object-detector **evaluation candidates**, not selected production models, are [`hustvl/yolos-tiny`](https://huggingface.co/hustvl/yolos-tiny) and [`facebook/detr-resnet-50`](https://huggingface.co/facebook/detr-resnet-50). Both are published as Apache-2.0 COCO object detectors; neither has demonstrated TIMS proctoring accuracy. The smaller model is the CPU-cost baseline. Pin exact revisions and hashes; compare candidate-device recall, false alarms, latency, memory, and licensing before choosing. Compare [Rekognition `DetectLabels`](https://docs.aws.amazon.com/rekognition/latest/dg/labels-detect-labels-image.html) on the same labeled person/phone task as a pay-per-image cost/quality baseline; keep a Hugging Face model only if it contributes measured value. If no candidate meets the agreed acceptance criteria, keep person/phone findings disabled while the rest of the evidence workflow operates. A GPU or SageMaker endpoint is **not** part of the default beta bill. [SageMaker asynchronous inference](https://docs.aws.amazon.com/sagemaker/latest/dg/async-inference.html) is the scale-up option if a validated model exceeds Lambda's CPU/latency envelope; a standing [real-time endpoint](https://docs.aws.amazon.com/sagemaker/latest/dg/realtime-endpoints.html) requires a measured latency or volume need.

## Capture policy, trust, and findings

- Start only after separate assessment, camera, screen, and media-storage notice/consent. The consent record includes notice version and server timestamp. Do not silently turn an existing unproctored assignment into a proctored one.
- While active, keep at-most-1-Hz local *positioning feedback only*; do not send BlazeFace-derived face-count events to the server. For cloud evidence, the local browser schedules **one camera and one entire-display still about every 65–75 seconds**, plus no more than **five event-triggered images of each type** per 30-minute assessment. The server permits at most 30 periodic and five event stills per type, with a minimum 55-second spacing for periodic stills. The browser offers media consent only for an explicitly timed 1–30 minute assessment; longer or untimed assessments keep event-only monitoring. Exact resolution/compression and sampling cadence are tunable only after labeled accuracy, usability, and cost measurement. No continuous raw video is retained.
- Screen evidence is restricted human-review material; no OCR or automatic classification of personal content in the first beta. A failed screen track, tab switch, or camera stop remains a separate event even when a screenshot cannot be captured. The UI shows capture status and a recovery path.
- Evidence metadata contains tenant, session, assignment, type, reason, server time, checksum, processing state, and expiry. Findings include the evidence ID, detector, pinned revision, label, confidence, server inference time, and failure reason. Do not store face embeddings. Reviewers see signed, short-lived reads with an audit record; recruiters and leaders retain no integrity-evidence access.
- An observation is an **unverified cue**. Confirmed media findings can corroborate it, but a missing image, model failure, or candidate network outage becomes `monitoring_unavailable` and a reviewer task, never a clean result or an automatic fail. Signed uploads establish an authenticated upload path, not camera authenticity.
- A high-severity *operational* alert (for example, prolonged server-observed heartbeat gap or sustained camera/screen loss) goes to authorized staff promptly without waiting for inference. An AI-generated person/phone finding may raise a review alert only after a validated threshold and corroboration policy. Alert text describes the observation, never alleges cheating. Staff can mark `clear`, `concern`, or `inconclusive` and record the candidate's explanation.
- The TypeScript assessment-submit / .NET proctoring-complete split remains a known non-atomic boundary. Result and media jobs are keyed by assignment/session and may arrive after submit; queue/result handlers reconcile idempotently. A later assessment-domain C# cutover should remove that split, but it is not required to build a truthful beta workflow.

## Security, retention, and operations

- Private S3 Standard bucket in the same region as the API/database; block public access, enforce TLS, SSE-KMS, exact-key staging POST policy, per-service least-privilege IAM, and separate media prefixes per tenant/session. [S3 SSE-KMS](https://docs.aws.amazon.com/AmazonS3/latest/userguide/UsingKMSEncryption.html) and [Bucket Keys](https://docs.aws.amazon.com/AmazonS3/latest/userguide/bucket-key.html) protect data and reduce KMS request cost. The API role must have the scoped KMS permissions needed for checksum-aware HEAD/copy/read; the inference role gets only sealed-key read. No public objects, face collection, or long-lived candidate download links. Audit reviewer URL issuance in .NET and enable S3 object-level data events if actual GET audit is required, budgeting for those events.
- Media access ends seven days after capture. The API refuses expired reads and caps signed GET validity to the remaining window. A .NET API-hosted purge checks every five minutes under a database advisory lock so replicas do not race; it marks rows expired before deleting staging/sealed objects and retries failed deletes. Each seal attempt uses a unique key and failed confirmation compensates by deleting its uncommitted copy when database state can be established; process death and unresolved network failures rely on lifecycle cleanup. The physical deletion SLO is therefore distinct from the exact read cutoff and must be monitored. [S3 lifecycle expiration](https://docs.aws.amazon.com/AmazonS3/latest/userguide/lifecycle-expire-general-considerations.html) is a backstop, not an exact clock. Avoid versioning or explicitly purge noncurrent versions, since ordinary expiration can leave old versions. Do not replay inference or draw an adverse conclusion after the underlying media has expired. Escalate unreviewed alerts before seven days, and define a staff review SLA shorter than retention. Candidate statements are readable only through the seven-day window and then purged. Finding/review metadata needs a separately approved HR record period. The local subject-access export includes bounded proctoring metadata and statements; physical-media disclosure and erasure still need an approved, audited fulfillment process.
- Add SQS request/result queues and DLQs, Lambda ECR deployment, KMS key/bucket policies, a bounded App Runner IAM policy, and feature flags by Terraform **after reconciling the existing live App Runner service with Terraform state**. Do not `terraform apply` the current module blindly. The API needs scoped S3 sign/HEAD/GET/copy/delete, KMS encrypt/decrypt/data-key, SQS send/receive, and the relevant secret reads; the Python role needs sealed-evidence read/decrypt, Rekognition call, and result send. Restrict both roles by bucket/key prefix, queue ARN, and KMS key. CloudWatch metrics cover consent/start failures, media upload failures, queue age/DLQ, model unavailable, event-to-alert delay, deletion lag, image counts, and cost. Never log candidate images or PII.
- Feature flags: global `Platform:ProctoringEnabled` remains off by default; separate `MediaEvidenceEnabled`, `CloudInferenceEnabled`, and per-org entitlement/policy gates. Candidate API rate limits resolve the authenticated candidate, so 25 people behind one company IP have independent bounded budgets. Disabling `CloudInferenceEnabled` stops new work; a provisioned Lambda mapping and the .NET outbox/result consumers continue draining confirmed work until queues and outbox are empty. A failing cloud model does not block completion of an assessment. Staff see `unavailable` and the reason. Only a consented pilot organization is enabled after staging gates pass.
- Keep all resources in `us-west-2` for the initial design because the existing API and Supabase data plane are there; verify contractual data-residency requirements before external media collection. The proposed first-company quota is 1,000 camera and 1,000 screen upload intents per organization per UTC day, enforced atomically in .NET. This limits each pilot organization's admission but is **not an account-wide spending ceiling**; an AWS Budget alerts on spend and does not stop charges. Add an explicit account-wide stop rule if the number of entitled pilot organizations grows. No always-on SageMaker or NAT gateway by default; if a private networking requirement changes that, recalculate the monthly fixed cost before rollout.

## Cost envelope and scaling trigger

The controls are **per-session capture caps** and no standing GPU. With 25 candidates taking a 30-minute exam, one camera and one screen image per minute plus at most five extra of each means a maximum of **1,750 images** per simultaneous cohort. Of these, at most **875 camera images** invoke Rekognition and the Hugging Face detector. If *both* image types averaged an illustrative **150 KB**, the cohort would upload about **0.26 GB**; full-display images may be substantially larger, so measure camera and screen bytes and p95 separately. AWS's [published Rekognition Group-2 example](https://aws.amazon.com/rekognition/pricing/) uses **$0.001 per image** for its first tier, implying about **$0.88 in DetectFaces calls** for this cohort; this is **not** a verified Oregon quote or a complete bill. Lambda duration, S3 requests/storage, KMS, SQS, logging, reviewer egress, and any liveness check are additional. Confirm regional prices and expected monthly volume in AWS Pricing Calculator before deployment.

For comparison, uploading one camera frame per second for the same cohort would produce **45,000 cloud face calls** and roughly **$45** at that illustrative per-image rate, before the extra privacy exposure and other costs. Monthly spend is proportional to the number of completed assessments, not just peak concurrency. The budget worksheet must use measured average media bytes and Lambda GB-seconds and report cost per completed assessment, per 100 and per 1,000 assessments, and at 25 simultaneous candidates. [SQS pricing](https://aws.amazon.com/sqs/pricing/) and [Lambda pricing](https://aws.amazon.com/lambda/pricing/) are usage-based; do not depend on account-wide free tiers. Do not use S3 Standard-IA for seven-day small objects because its [minimum billed size and duration](https://aws.amazon.com/s3/pricing/) undermine that choice.

| Thirty-minute assessments/month | Maximum camera analyses | Maximum total stills | Illustrative DetectFaces calls at $0.001/image |
| ---: | ---: | ---: | ---: |
| 100 | 3,500 | 7,000 | $3.50 |
| 500 | 17,500 | 35,000 | $17.50 |
| 1,000 | 35,000 | 70,000 | $35.00 |

These figures assume every session consumes its five extra camera and five extra screen captures and use the AWS example rate, **not** a regional quote or a total AWS estimate. They exclude Lambda duration, S3, KMS, SQS, logging, egress, model reprocessing, and any liveness check. The final deployment gate uses actual monthly volume and measured image/model sizes in the Oregon AWS calculator.

Scale to SageMaker only if the selected model cannot meet the agreed p95 processing latency, accuracy, and cost per assessment in Lambda at the measured peak. Asynchronous inference can scale instances to zero but has queue/startup latency; it cannot be the only immediate-alert mechanism. [SageMaker Serverless Inference excludes VPC configuration, network isolation, GPU, data capture, and Model Monitor](https://docs.aws.amazon.com/sagemaker/latest/dg/serverless-endpoints.html), so do not assume it is the right security/cost tradeoff for sensitive candidate images.

The first Terraform setting caps Lambda at **two concurrent executions**. At the maximum 875 camera images in a 25-candidate cohort, draining the cohort within 15 minutes requires an observed mean worker time below about **2.1 seconds per image** when both slots remain busy (`875 × time / 2 ≤ 900 seconds`). Cold starts, retries, and overlapping cohorts reduce that margin. Benchmark the pinned image in the actual region and raise concurrency or lower sampling only from measured queue age, reviewer delay, and cost; browser/heartbeat operational alerts do not wait for this queue.

### Implementation checkpoint

The local branch now contains the .NET 10 media endpoints and S3 sealing/read/deletion services, tenant-scoped evidence and finding repositories, an outbox/SQS result path, a pinned-artifact Python Lambda worker, disabled-by-default Terraform resources, candidate still-capture UI, restricted staff media review, a one-shot candidate statement with review-race protection, a tenant-scoped operational alert inbox sweep, and bounded audited subject-access metadata export. These are **implemented locally**, not a deployed or end-to-end-verified service. Database, web, .NET, worker, and Terraform checks must all pass on the final combined diff. The Hugging Face detector remains off by default. The initial cloud face baseline is an observation for a human reviewer, not an adjudication.

The release-critical remaining work is: reconcile the real AWS account/App Runner/Terraform state; apply the migration in staging; verify signed browser POST/CORS/CSP and KMS permissions against real S3; run request/result queue and Lambda replay/DLQ tests in AWS; prove physical deletion timing and the operational alert SLA on real devices; establish an audited physical-media disclosure/erasure process; agree the notice and retention for non-media records; evaluate labeled TIMS device samples with false-alert thresholds; and perform the 25-candidate load/cost trial. Keep all media/cloud flags off until those gates pass.

The test set must include low light, face coverings, glasses, movement, multiple people, phones at different sizes/positions, screen-share stop/window-only choice, network loss, reload, device unplug, and accessibility accommodations. Report event-level precision/recall and **false alerts per clean assessment**; report misses by device and relevant candidate groups with confidence intervals. A COCO benchmark or synthetic webcam test is not a TIMS accuracy result. Agree numerical pass thresholds with TIMS before using model findings as production alerts. Until then they remain labeled experimental findings for staff-only evaluation. No claim of SMOWL parity or a percentage accuracy is justified by the current tests.
